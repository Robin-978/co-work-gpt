# 看得見的 LLM — 動態演示語言模型怎麼運作

`llm/index.html` 是一個**單檔、零後端、離線可跑**的網頁，用動畫一步一步演示一個語言模型
從輸入到輸出的完整過程：

1. **Tokenization 分詞** — 文字切成 token，查表換成 id
2. **Embedding 詞向量** — token 向量 ＋ 位置向量
3. **Self-Attention 注意力** — Q·K → softmax → 加權混合 V（含因果遮罩）
4. **Feed-Forward 前饋網路** — 向量維度放大（64 → 192）、GELU、再壓回來
5. **Generation 產生** — logits → 溫度 → softmax → Top-K → 抽樣
6. **Output 輸出** — 新字接回輸入，回到第 1 步（自迴歸）

畫面上的每一個色塊、每一條長條，都是模型**當下在瀏覽器裡算出來的真實數值**，不是預錄的示意動畫。

## 模型

不是呼叫任何 API，而是一個從零訓練的 char-level GPT，權重以 int8 量化後直接內嵌在 HTML 裡：

| 項目 | 值 |
|---|---|
| 參數量 | 134,976 |
| 層數 / 注意力頭 | 2 layers / 4 heads |
| 向量維度 | d = 64（head_dim 16）|
| 前饋層 | 192 |
| 上下文長度 | 48 tokens |
| 字典 | 755 個字元（中文、英文縮寫、數字、標點）|
| 訓練語料 | 437 句，45,780 字：III/V 族磊晶半導體 + SPC 統計製程管制用語 + 良率可靠度 + 金融財經，另含少量日常句 |

架構跟 GPT 完全一樣（pre-LN Transformer decoder、causal self-attention、weight-tied 輸出頭），
差別只在規模。因為語料極小，它只會講這個領域裡、很像訓練資料的句子——這正好讓「模型在背下來的分布裡取樣」
這件事變得看得見。

語料同時涵蓋磊晶製程與 SPC，還刻意寫了一批交叉句（例如「波長的管制圖出現趨勢，通常和溫度有關」），
所以模型會把兩個領域接在一起講。字典裡也有英文縮寫與數字，剛好可以在 Step 1 看到
`MOCVD` 被切成 5 個 token、而中文一個字只佔 1 個 token 的對比。

內附的 `weights.json` 是**從零訓練 4,800 步 + 續訓約 6,500 步**（含金融語料）的結果。
頁面預設溫度 0.9：太低或太收斂，Step 5 就只剩一根 100% 的長條，看不出 softmax 在做什麼；
太高則續寫會散掉。目前 `MOCVD 的成長` 這個提示會給出
溫 46.7% / 壓 34.6% / 速 18.5%（熵 1.52 bits）——三個都是語料裡真的出現過的接續
（成長溫度／成長壓力／成長速率），所以這種多峰是結構性的，不會因為多訓練而消失。

## 重新訓練 / 重新打包

```bash
cd llm/tools
node train.js gradcheck      # 反向傳播的數值梯度檢查
node run_train.js            # 訓練（預設 7000 步、約兩小時），過程中會定期寫出 weights.json
node probe.js                # 驗收：字典健康度、機率分布、實際續寫
node build.js ../index.html  # 把 weights.json 內嵌進 page.template.html
```

超參數可以用環境變數覆寫，不用改程式：

```bash
STEPS=3000 DIM=48 HEADS=3 FF=128 BATCH=12 LR=3e-3 node run_train.js
```

- `corpus.js` — 訓練語料（改這裡就能換模型會講的話）
- `train.js` — 純 JS 的 forward / backward / 梯度檢查
- `run_train.js` — AdamW 訓練迴圈 + int8 量化輸出
- `probe.js` — 檢查工具：語料/字典健康度、機率分布、熵、實際續寫（也可被其他工具 require）
- `ingest.js` — 把文獻／報告的純文字洗成可訓練的語料塊（長句過濾、稀有字元反覆剪枝）
- `rag_demo.js` — RAG 的最小示範：檢索 → 組裝 prompt → 生成，並對照有無檢索的差異
- `epi_calc.js` — III/V 磊晶的專家系統核心：材料表、Vegard、Varshni、四元匹配、XRD、量子井、bubbler、電性量測
- `fin_calc.js` — 金融財經的專家系統核心：複利、房貸、NPV/IRR、DCF、債券、Black-Scholes、風險績效
- `epi_data.js` — EPI 生產資料的查詢函式層：讀 CSV/TSV（UTF-8 與 Big5 自動辨識）、統計、Cpk、分組比較、SPC 判異、離群爐次、相關
- `expert.js` — 把三個領域包成一份「LLM 可呼叫的工具目錄」，含 function-calling 用的 JSON 定義
- `page.template.html` — 網頁模板，`__WEIGHTS__` 會被換成權重
- `build.js` — 打包成單一 HTML

只改網頁不重訓的話，編輯 `page.template.html` 後跑 `node build.js ../index.html` 即可。

## 擴充字典（讓模型認得更多字）

字典不是一份手動維護的清單，而是從語料**自動長出來的**（`run_train.js`）：

```js
const chars = Array.from(new Set(Array.from(text))).sort();  // 語料出現過的字元 = 字典
const cfg = { V: chars.length, ... };
```

所以「擴充字典」＝「**擴充語料 + 重訓**」。沒辦法只加字不重訓：新字的 embedding 是隨機初始化的，
沒被訓練過就只是亂數，模型不會拿它接任何東西。

### 步驟

```bash
cd llm/tools
#（1）編輯 corpus.js 的 SENTENCES，加入新句子
node probe.js                 #（2）看字典健康度：哪些字出現太少
STEPS=4000 node run_train.js  #（3）重訓
node probe.js 0.9             #（4）驗收：分布合不合理、續寫通不通順
node build.js ../index.html   #（5）打包回網頁
```

頁面上的「字典 N tokens」「參數量」是從權重檔讀出來的，不用手動改。
若新增了新主題，記得同時更新 `page.template.html` 裡的預設 prompt 與範例按鈕（`.preset`）。

### 語料要加多少

關鍵不是字典多大，而是**每個字出現幾次**。目前是 45,780 字 ÷ 755 字元 ≈ 每字 61 次。`probe.js` 會直接把出現不到 10 次的字列出來——那些字學不到，
只會變成 Top-K 候選裡的雜訊。

**經驗法則：平均每字 ≥ 20 次，且每個字要出現在多個不同的上下文裡。**
只在一句話裡出現過的字，模型學到的只是「背這句話」。

`buildCorpus()` 把每句重複 6 次，所以一個只出現在一句裡的字＝6 次。加字典時要嘛多寫幾句
用到同一個字，要嘛提高重複次數（但重複不會增加資訊，只會讓它更死記）。

### 用文獻／報告餵語料（`ingest.js`）

先講清楚哪些東西會被文獻改變：

| | 上傳文獻能改嗎 | 為什麼 |
|---|---|---|
| 字典 | ✅ 自動長大 | 字典就是語料裡出現過的字元集合 |
| 參數量 | ⚠ 只長一點，而且是副作用 | 字典 +100 → 詞向量表多 100×64；`d`／層數／FFN 完全不受影響 |
| 上下文 | ❌ 完全不會 | `B=48` 是架構選擇，跟資料無關 |

**直接把論文全文倒進去會讓模型變差**，有兩個原因：

1. **稀有字元爆炸。** 一篇論文帶進幾百個只出現兩三次的字（人名、單位、罕用術語）。
   字典變大 → 輸出層每一步要多算幾百個分數，而那些字學不到任何東西，只會變成 Top-K 裡的雜訊。
2. **句子太長。** 上下文只有 48 個 token，論文裡 80 字的長句模型永遠看不到完整一句，
   學到的只是斷片。

所以 `ingest.js` 做的是那道清洗：

```bash
node ingest.js 論文資料夾 -o papers.js -n PAPERS     # 只吃 .txt / .md
node ingest.js a.txt b.md --min 12 --max-len 40
```

逐句丟掉：太短、太長（塞不進上下文）、沒有中文、參考文獻與網址、編號開頭、圖表標題、
中文比例 < 45%（公式或英文夾雜）、標點 > 30%（表格殘片）、重複句。全形英數字會正規化成半形，
免得 `ＭＯＣＶＤ` 和 `MOCVD` 被當成兩組不同的字。

**關鍵在最後一步：稀有字元反覆剪枝。** 判斷基準是「合併既有語料之後」的次數，不是文獻本身的次數——
「量」在文獻裡只出現 3 次不代表它稀有，既有語料裡它可能已經有幾百次；反過來，
文獻獨有的字就算在文獻裡出現 5 次，合併後還是 5×6=30 次還是 5 次，要看它是不是新字。
剪掉含稀有字的句子以後別的字次數也會跟著掉，所以要**反覆做到收斂**，不能只掃一遍。

報告會直接告訴你代價：

```
留下 7 句，187 字，用到 101 個字元
文獻用到的字元裡，合併後最冷門的是「約」，出現 12 次（門檻 10）
其中 0 個字元是現有語料沒有的：
  字典 755 → 755，詞向量表多 0 個參數
```

新字超過 40 個會警告「續訓多半學不起來，建議從零訓練」——這跟 `run_train.js` 的門檻一致。

### 但文獻問答不該用這條路

要注意這整節解的是「讓模型的語感涵蓋這個領域」，**不是「讓模型會回答文獻內容」**。
後者在這個規模做不到：前面 RAG 那節實測過，128K 參數的模型完全不理會檢索到的內容。
真的要做文獻問答，正確架構是**大模型 + RAG**（文獻放檢索庫，不進訓練），
或是像 `epi_calc.js` / `fin_calc.js` 那樣把可計算的部分交給程式。

### 規模與代價

| 字典 | d / FFN | 參數量 | 權重（base64） | 訓練成本 | 建議語料 |
|---|---|---|---|---|---|
| 304 | 48 / 128 | 61,120 | ~80 KB | 1.0× | 7 千字 |
| 755（現況） | 64 / 192 | 134,976 | ~182 KB | 2.5× | 4.6 萬字 |
| 1,500 | 64 / 192 | 182,656 | ~238 KB | 3.8× | 4 萬字 |
| 3,000 | 64 / 192 | 278,656 | ~363 KB | 6.5× | 8 萬字以上 |

（訓練成本是相對現在 3,000 步約 16 分鐘而言；輸出層要對整個字典算分數，所以成本大致隨字典線性成長。）

字典超過 ~600 時要把模型調大，否則 48 維裝不下那麼多字的差異（現在的預設已經是 `DIM=64 HEADS=4 FF=192`）。
`DIM` 必須能被 `HEADS` 整除；改 `BLOCK`（上下文長度）也要重訓，因為位置向量表的大小跟著變。
網頁端會自動照權重檔裡的 `cfg` 調整，不用改前端程式。

語料換主題以後，記得同時更新 `page.template.html` 裡的預設 prompt 與 `.preset` 範例按鈕。

### 不建議的做法

把一份常用字表硬塞進語料來「湊字典」。那些字沒有真實的上下文，模型只會學到它們的邊際機率，
在 Top-K 裡冒出來卻接不成句子——字典變大了，輸出品質反而變差。

## 產出有錯的時候怎麼修

模型沒有一張「事實表」可以改。輸出只是三件事的結果：**語料**、**訓練程度**、**取樣設定**。
所以修正一定發生在這三個地方之一——而第一步永遠是**先診斷是哪一種錯**，不要用猜的。

### 第一步：用 probe.js 看出錯那一格的機率分布

```bash
node probe.js 0.9 "Cpk 大於 1.6"
```

關鍵只有一個問題：**正確答案的機率高不高？**

| 診斷 | 意思 | 怎麼修 |
|---|---|---|
| 正確答案機率很高，卻沒被選中 | 抽籤意外 | 降溫度 / 降 Top-K，**不用重訓** |
| 正確答案機率就低 | 模型沒學好 | 補語料變體、提高 `STEPS` |
| 模型很有信心，但講的是錯的 | 語料本身寫錯 | 改 `corpus.js` 重訓 |
| 出現「不在字典」警告 | 沒有這個字 | 擴語料重訓 |

### 實例：`Cpk 大於 1.63`

語料裡只有 1.33（能力足夠）和 1.67（能力很好），但模型曾經吐出 `1.63`。診斷結果：

```
"Cpk 大於 1."   → 6 93.3%  3 3.9%
"Cpk 大於 1.6"  → 7 97.5%  1 0.3%  6 0.2%  3 0.2%   ← 抽到了 0.2% 的「3」
"Cpk 大於 1.33 代表製程的能力" → 足 98.0%   ✓
"Cpk 大於 1.67 代表製程的能力" → 很 99.3%   ✓
```

模型其實知道答案（1.67 有 97.5%），是取樣抽到了 0.2% 的冷門。溫度降到 0.5 時，
同一格的分布變成 `6 100.0%`，這個錯就不會發生了。**這種錯不需要重訓，調溫度就好。**

反過來說，這也是「幻覺」的縮影：每一步都是一次抽籤，一段話跑幾十步，
再小的機率也遲早會被抽中——而且模型不會知道自己抽錯了。

### 另一種錯：短上下文本身就有歧義（這種訓練不掉）

加了金融語料以後，有兩格怎麼續訓都收斂不了，卡在五五波：

```
"複利是利息"       → ， 58.8%   再 31.0%
"分散投資可以降低"  → 。 61.9%   單 37.2%
```

正確答案是「複利是利息**再**滾利息」「分散投資可以降低**單**一標的的風險」。
模型不是沒學到——是「利息」後面在語料裡絕大多數真的接「，」（來自房貸那幾句），
「降低」後面也常常就句號結束。**在 char-level、48 tokens 上下文的規模下，
前面那幾個字提供的訊息量不足以壓過這個先驗。**

診斷方式一樣（看分布），但結論不同：這不是抽籤意外（正確答案沒有很高），
也不是訓練不足（1,700 步內完全沒有移動）。要修只有三條路——
**寫更多用到同一個前綴的句子**（讓「複利是」這個前綴本身變得有辨識度）、
**加大模型 / 上下文**，或**換成 word-level 斷詞**。
再多訓練步數是無效的，這點值得知道，免得白跑兩小時。

**這也是為什麼頁面預設溫度從 1.3 調成 0.9。** 字典從 660 長到 755、語料多了金融領域以後，
1.3 已經熱到會讓續寫散掉；0.9 續寫穩定，而 Step 5 的長條圖照樣有東西看
（`MOCVD 的成長` → 溫 46.7% / 壓 34.6% / 速 18.5%，熵 1.52 bits），
因為那三個候選是語料裡真的都存在的接續，不會因為退火而消失。

### 對照到真正的 LLM

| 這裡的做法 | 真實世界對應的東西 |
|---|---|
| 降溫度 / 調 Top-K | 完全一樣，就是推論參數 |
| 改語料重訓 | 清理預訓練資料 |
| 針對錯誤補寫正確例句再訓 | 微調（SFT）|
| 人工標出好壞再訓 | RLHF / 偏好對齊 |
| （本模型沒有）查完資料再回答 | RAG 檢索增強 |
| （本模型沒有）輸出後再檢查一次 | 護欄 / 事實查核 |

## 續訓（微調）：不用從頭來過

改一句語料就重訓兩小時太貴。`RESUME=1` 會**接著現有的 `weights.json` 繼續訓練**：

```bash
cd llm/tools
# 改完 corpus.js 之後
RESUME=1 node run_train.js          # 預設 900 步、LR 4e-4，約 18 分鐘
RESUME=1 STEPS=1500 node run_train.js   # 學不夠就再跑久一點
node probe.js 0.9 "你改的那句的開頭"
node build.js ../index.html
```

`RESUME=/path/to/其他檢查點.json` 可以指定別的檔案當起點。

### 它做了什麼

- **字典可以變大**：舊字的詞向量照「字」搬過來，只有新字隨機初始化。所以加句子、加術語都不必從零開始
- **結構不能變**：`DIM` / `LAYERS` / `HEADS` / `FF` / `BLOCK` 必須和檢查點一致，不一致會直接報錯並告訴你該用什麼值
- **預設值不同**：續訓是 900 步 / LR 4e-4（從零訓練是 7,000 步 / LR 2.5e-3）。學習率小才不會把原本學會的東西洗掉
- **會先量一次 loss**：載入後如果印出的是接近原本訓練到的值（例如 0.09），就確認真的接上了；
  如果接近 `ln(字典大小)`（約 6.5），代表根本沒載到
- **會自動備份**：原檢查點複製成 `weights.prev.json`，續訓壞掉可以直接還原

### 實測：續訓能做到什麼、做不到什麼

在 649 字典的模型上加了 12 句「良率與可靠度」（引進 11 個新字元），分兩輪續訓：

**第一輪 900 步（18 分鐘）**——句首學會了，但整句往下會散掉，**全新的字元幾乎沒學起來**：

| 提示 | 正確接續 | 900 步後 |
|---|---|---|
| `良率是通過測試的` | 片（數）| 85.6% ✓ |
| `8D 是一套` | 處（理）| 78.6% ✓ |
| `老化測試可以先` | **篩**（掉）——新字元 | **8.2%**（熵 6.99 bits）✗ |

**第二輪再 1500 步（31 分鐘，累計 2,400 步）**——新字元才真的學起來：

| 提示 | 900 步 | 累計 2,400 步 |
|---|---|---|
| `老化測試可以先` | 篩 8.2% | **篩 64.4%** |
| `8D 是一套` | 處 78.6% | 處 91.5% |
| `可靠度測試是用加速的` | — | 條 98.5% |
| `失效分析要先` | — | 確 89.6% |

**而舊的東西自始至終沒有被洗掉**——這是續訓最該擔心的事（災難性遺忘），實測沒有發生：

| 提示 | 續訓前 | 累計 2,400 步後 |
|---|---|---|
| `量子井的` | 厚 98.5% | 厚 99.1% |
| `Cpk 大於 1.6` | 7 97.5% | 7 97.1% |
| `MOCVD 的成長` | 壓 44 / 速 33 / 溫 17 | 溫 44 / 速 31 / 壓 22 |

（`MOCVD 的成長` 這三個候選是 成長溫度／成長速率／成長壓力，順序換了但三個都對。）

結論很直接：**續訓的成本和它要學會的量成正比**。

- 改錯字、改一句寫錯的話 → 900 步就夠
- 加一小批用**既有字元**寫的句子 → 900～1500 步
- 引進**新字元** → 新字的詞向量等於從零學，要 2,000 步以上；新字很多時乾脆從零重訓

`run_train.js` 在新字超過 40 個時會直接警告你這件事。

### 一個技術細節

檢查點是 int8 量化的，所以續訓等於「反量化 → 訓練 → 再量化」。實測這個來回幾乎沒有損失
（載入後 loss 0.1056，原本訓練到的是 0.09，差距在取樣誤差內），但如果反覆續訓很多輪，
量化誤差會慢慢累積——真的要做很多輪的話，建議每隔幾輪從零重訓一次當基準。

## RAG 是怎麼跟 LLM 合作的

`tools/rag_demo.js` 是一個可以直接跑的最小示範：

```bash
node rag_demo.js                    # 三組對照：同一個問題，有檢索 vs 沒檢索
node rag_demo.js "你想問的問題"
```

### 它其實只有三步，而且只有第三步跟模型有關

```js
const hits = retrieve(question);              // 1. 檢索：普通的字串／向量比對
const prompt = hits[0].doc + '\n' + question;  // 2. 組裝：只是字串相接
const logits = fwd(encode(prompt));           // 3. 生成：同一個模型、同一組權重
```

**RAG 完全不碰模型的權重**。它改的是「模型看到什麼」，不是「模型知道什麼」。
所以它不用重訓，換一份知識庫就換一套答案——這是它相對於微調最大的優點：

| | 微調 / 續訓 | RAG |
|---|---|---|
| 改什麼 | 權重 | prompt |
| 成本 | 要跑訓練 | 一次檢索 |
| 更新知識 | 重訓 | 換資料庫的內容 |
| 出處 | 說不出來 | 可以附上檢索到的原文 |
| 適合 | 改變**風格、格式、講話的方式** | 提供**會變動的事實** |

### 但這個示範同時證明了 RAG 的前提

知識庫裡放的是模型沒學過的內容（本廠 Cpk 標準 1.50、成長溫度 720 度、載盤 1200 轉），
檢索也確實抓對了文件。結果：

```
問題：Cpk 大於 1.        檢索到：本廠的規定是 Cpk 大於 1.50 代表能力足夠。
  沒有檢索 → 3 58.5%  6 34.2%     「5」不在前五名
  有檢索　 → 6 96.2%  3  1.1%     「5」仍然不在前五名
```

**模型完全不理會檢索到的內容**，照樣講訓練時背下來的 1.33 / 1.67。
更有意思的是有檢索之後它反而**更確定**要接 6（34% → 96%）——
它有注意到上下文，只是把上下文當成「這是在講 Cpk」的線索，
而不是「這裡有一個我該照抄的數字」。另外兩組（720 度、1200 轉）也一樣失敗。

會照抄上下文的能力叫 **in-context learning**，要模型大到一定程度才會浮現。
所以結論是：**RAG 不是模型的一個功能，而是模型的一種用法；能不能用，取決於模型夠不夠大。**
這也是為什麼 RAG 是在 GPT-3 那個級距之後才變成標準做法。

（順帶一提，`rag_demo.js` 會在 prompt 超過 48 個 token 時警告你前面被截掉了——
上下文長度是 RAG 的硬限制，塞太多檢索結果反而會把問題本身擠出去。）

## 專家系統 + LLM：精準度真正的來源

三支程式，一條線：

```bash
node epi_calc.js     # III/V 磊晶：14 項自我測試 + 範例
node fin_calc.js     # 金融財經：16 項自我測試 + 範例
node expert.js       # 工具目錄：36 個確定性函式，兩個領域
```

### 為什麼需要它：模型不會算，只會背

問模型一個它背過的事實，答案是對的；問一個它沒背過的，它會**用同樣的自信講錯的數字**：

```
"砷化鎵基板的晶格常數是 "   → 5 100.0%   （接出 5.653 埃，正確）
"砷化鋁鎵的晶格常數是 "     → 5  99.9%   （也接出 5.653 埃，錯——那是 GaAs 的值）
```

熵 0.01 bits，它一點都不覺得自己在猜。**因為晶格常數是一個「隨組成連續變化的函數」，
不是一個可以背下來的事實**——AlxGa1-xAs 有無限多種組成，模型能背的只有它看過的那一個。
複利、IRR、Black-Scholes 也完全一樣：那些是函數，不是事實。

而這件事根本不該用「記憶」解決：

```
Al0.3Ga0.7As：晶格 5.65561 Å　能隙 1.820 eV　波長 681.2 nm　與 GaAs 不匹配 0.0417%
房貸 100 萬、年利 2%、30 年：月付 3696.19 元，總利息 330,630 元（本金的 33.1%）
```

### 角色分工

| 角色 | 負責什麼 | 不負責什麼 |
|---|---|---|
| **專家系統**（`epi_calc` / `fin_calc`）| 算數字、查表、套規則 | 聽懂人話 |
| **LLM** | 聽懂問題、挑對函式、填對參數、把結果講成人話、缺參數時反問 | **產生任何數字** |

差別在於：RAG 是把資料放進 context 讓模型「自己讀」，模型仍可能讀錯；
專家系統是模型**呼叫**一段確定性的程式，數字由程式算出來，模型只是轉述——
**這條路上沒有幻覺的空間**。

### `epi_calc.js`：III/V 磊晶

材料表含 16 種材料（閃鋅礦 III/V、纖鋅礦 III/N、Si/Ge 基板、藍寶石），
標記晶體結構，**不同結構混用會直接報錯**（GaAs 和 GaN 不能用 Vegard 內插）。

| 函式 | 算什麼 |
|---|---|
| `latticeConstant` / `bandgap` | Vegard 三元晶格常數、能隙（含彎曲參數）|
| `bandgapAtTemperature` | Varshni 溫度相依——解釋「成長溫度飄一點，室溫波長就跟著變」|
| `quaternaryLattice` / `quaternaryMatchedX` | 四元合金（InGaAsP 長在 InP 上要配多少 Ga）|
| `mismatch` / `inPlaneStrain` / `criticalThickness` | 不匹配度、應變、Matthews-Blakeslee 臨界厚度 |
| `dSpacingCubic` / `braggAngle` | XRD 晶面間距與 2θ |
| `quantumWellEnergy` | 量子井基態能階（估藍移）|
| `vaporPressure` / `bubblerMolarFlow` / `vIIIRatio` | 前驅物蒸氣壓、莫耳流量、V/III 比 |
| `hallCarrierConcentration` / `fourPointSheetResistance` | 霍爾載子濃度、四點探針片電阻 |
| `growthRate` | 成長速率換算 |

**14 項自我測試**釘在已知物理上：In0.53Ga0.47As 匹配 InP、Al0.3Ga0.7As 1.80 eV、
GaAs (004) 2θ = 66.05°、10 nm 井基態 56 meV、TMGa 在 0 °C 蒸氣壓 65 Torr、
四點探針係數 π/ln2 = 4.5324，外加一項「該擋的要擋下來」。

### `fin_calc.js`：金融財經

| 函式 | 算什麼 |
|---|---|
| `futureValue` / `presentValue` / `annuityPV` / `cagr` | 貨幣的時間價值、年金、年化報酬 |
| `effectiveAnnualRate` / `realRate` / `doublingTime` | 有效年利率、Fisher 實質利率、翻倍年數（含 72 法則對照）|
| `loanPayment` / `amortize` | 房貸月付、已付利息、剩餘本金、總利息 |
| `npv` / `irr` / `paybackPeriod` / `dcfValue` / `wacc` | 投資評估與估值 |
| `bondPrice` / `bondYTM` / `bondDuration` | 債券定價、殖利率反推、存續期間與凸性 |
| `blackScholes` / `impliedVol` | 歐式選擇權定價、Delta、隱含波動度反推 |
| `sharpe` / `annualVol` / `maxDrawdown` | 風險與績效 |
| `breakEvenUnits` / `dupontROE` / `purchasingPower` | 損益兩平、ROE 杜邦拆解、購買力 |

**16 項自我測試**釘在課本標準答案上：房貸 100 萬 / 2% / 30 年月付 3696.19、
債券（面額 100、票息 5%、3 年、YTM 6%）價格 97.327、Macaulay 存續 2.857、
Black-Scholes（S=K=100、r=5%、σ=20%、T=1）買權 10.4506、
以及「由價格反推 YTM 應回到 6%」「由市價反推隱含波動度應回到 20%」這種來回一致性檢查。

### `expert.js`：交給 LLM 的那份清單

```bash
node expert.js                 # 列出 44 個工具（磊晶 15 + 金融 21 + 生產資料 8）
node expert.js --data runs.csv processCapability 波長 1540 1560 MOCVD-03
node expert.js --schema        # 印出 function-calling 用的 JSON 定義
node expert.js bandgap AlAs GaAs 0.3
node expert.js loanPayment 1000000 0.02 30
node expert.js --json bondDuration '{"face":100,"couponRate":0.05,"years":3,"ytm":0.06}'
```

真實系統裡 LLM 拿到的不是知識，而是這份函式清單。模型不需要「知道」Black-Scholes
或 Vegard 定律，只需要挑對函式、填對參數。

有一個行為特別值得注意——**參數不齊時它會反問，不會自己填**：

```
$ node expert.js blackScholes 100 100 0.05
✗ 缺少參數：sigma、T。請補齊後再算，不要用猜的。
```

這正是把「不知道」變成一個明確狀態，而不是讓模型用一個看起來合理的數字補上去。

### 關於機台參數（Aixtron G3/G4 之類）

`MACHINES` 這張表**刻意留空**，查不到的時候會直接說「不在參數表裡，請填入實機資料——不要用猜的」。

1. 各廠的機台配置、recipe 與校正值都不一樣，沒有「通用的正確答案」
2. 這類參數多屬廠商與製程機密，不該由任何模型憑印象產生
3. **一旦填進表裡，它就從「模型可能記錯的東西」變成「查表查得到的事實」**

### `epi_data.js`：生產資料的查詢函式層

前面幾支解的是「**可計算**」的東西。爐次數據是另一半：「**可查詢**」。

```bash
node epi_data.js --demo        # 產生範例資料（240 爐、3 台機、40 天）並跑一輪查詢
node epi_data.js --test        # 33 項自我測試
node epi_data.js runs.csv --cpk 波長 1540 1560
```

支援 CSV / TSV，**UTF-8 與 Big5 自動辨識**——台灣的 MES 與 Excel 匯出常常是 Big5，
當成 UTF-8 讀會整片亂碼。欄位名稱透過 `COLUMN_ALIASES` 對應（爐號/RunID/LotID…），
第一次接資料時要對著真實表頭補上你家系統的寫法。

| 函式 | 回答什麼 |
|---|---|
| `runStats` | 筆數、平均、標準差、四分位、最大最小 |
| `cpk` | 製程能力 Cp / Cpk |
| `groupStats` | 各機台／產品／每日／每月比較，含組間最大差距 |
| `spcRules` | 管制圖判異：超三倍標準差、二/三倍區、連續七點同側或持續上升下降 |
| `outliers` | 偏離 k 倍標準差的爐次清單（含爐號） |
| `correlate` | 兩個量測值的相關係數與斜率 |
| `runDetail` / `listRuns` | 單爐查詢、爐次清單 |

**為什麼是參數化函式，不是讓模型自由寫 SQL：**

1. **可測試**——函式可以釘在手算得出來的答案上，自由生成的 SQL 不行
2. **安全**——不可能掃全表、不可能查到不該查的欄位、不可能寫入
3. **可驗證**——回答時附得上「用了哪個函式、哪些參數、幾筆資料」

現場九成的問題就是上面這十幾種，長尾才需要人工下 SQL。

**兩個刻意的行為**，跟 `epi_calc.js` 拒絕猜機台參數是同一個原則：

```
n < 25 的 Cpk 會警告「不可靠，只能當參考」   ← 5 筆資料的 Cpk 是噪音，不能默默算給你看
沒給 lsl / usl 會直接擋下                    ← 規格界限不能用猜的
```

`--demo` 還示範了一個現場常犯的錯：範例資料裡真正的溫度係數是 0.6 nm/°C，
單看乾淨的兩台機台都算得回來（0.620、0.604），但把偏移的第三台混進去一起算會變成 0.845。
**混機台算相關會失真**，所以每個查詢函式都吃 filter，逼你先分群再看關係。

### 什麼問題該用什麼

| 問題性質 | 例子 | 該用 |
|---|---|---|
| 可計算 | 「Al 三成的 AlGaAs 發光波長？」「這筆房貸總利息多少？」 | `epi_calc` / `fin_calc` |
| 可查詢 | 「上個月 3 號機波長的 Cpk？」「哪幾爐超出三倍標準差？」 | `epi_data` |
| 可檢索 | 「這篇論文怎麼解釋波長偏移？」 | RAG 向量檢索 |
| 需要經驗與推理 | 「波長偏移 2 nm 可能是什麼原因？」 | LLM ＋ 上面三者 |
| 需要判定 | 「這批要不要判退？」「這個案子要不要投？」 | 規則引擎（**不要**交給 LLM）|

**可查詢和可檢索是兩件事，不能用同一套。** 生產資料丟進向量庫是必踩的坑：
「這批的波長平均值」這個答案不存在於任何一列裡，它是 GROUP BY + AVG 算出來的，
向量檢索只能撈「最像這句話的幾列」，永遠算不出平均。而且 embedding 分不出
600.2 和 620.5 哪個離規格近——那是數學，不是語意。

**精準度的問題會從「模型記得準不準」變成「公式對不對、參數表新不新」**。
後者是可以寫測試、可以版本控制、可以請資深工程師 review 的工程問題——這才是它真正的價值。

## 操作

- **開始演示 / 暫停 / 停止**（空白鍵 = 開始或暫停，Esc = 停止）
- **溫度**：越低越保守，越高越有創意也越容易亂講
- **Top-K**：只從機率最高的 K 個字裡抽
- **動畫速度**：0.5×–4×
- **每個字都完整演示 / 只完整演示第一個字**：後者會加快後續的字
- 注意力那一段可以切換**第幾層、第幾個頭**，看不同的頭在看什麼關係
