Inside a Language Model

看得見的 LLM：一個字是怎麼被想出來的

這一頁跑的是一個真的語言模型——一個在瀏覽器裡即時推論的迷你 Transformer。你輸入的每個字，都會實際走過 分詞 → 詞向量 → 注意力 → 前饋網路 → 取樣 → 輸出，畫面上的每個顏色格子、每條長條，都是它當下算出來的真實數值，不是示意動畫。

Step 1分詞 Tokenization

模型不認得文字，只認得數字。第一步是把輸入切成一個個 token，再用字典查出每個 token 的 id。 這個示範模型用「一個字元＝一個 token」的切法，所以中文一個字是一個 token，而 MOCVD 會被切成 5 個 token——英文和數字天生就比中文吃 token。ChatGPT 這類大模型用的是 BPE，一個 token 通常是半個英文單字或一小段中文詞。

Step 2詞向量 Embedding

每個 token id 會去查一張詞向量表，換成一串數字（本模型是 維）。這串數字就是這個字的「意思座標」。 再加上一個只跟位置有關的向量，模型才知道誰先誰後——底下每一直行就是一個 token 的向量， 橘色為正、藍色為負、越暗越接近 0。

Step 3注意力 Self-Attention

這是 Transformer 的核心。每個字都會問前面所有的字：「你跟我有多相關？」——用 Q·K 算出分數， 再經 softmax 變成加總為 1 的權重，然後把大家的 V 按權重混合起來。 因果遮罩讓每個字只能看見自己和左邊的字（所以熱圖是下三角形）。

Step 4前饋網路 Feed-Forward

注意力負責「跟別人交換情報」，前饋網路負責「自己想一想」。它把 維先放大到 維， 用 GELU 激活函數過濾掉沒用的訊號，再壓回 維。多數模型有一半以上的參數都放在這裡，知識大多存在這一層。

激活值越大 = 這個「神經元」越興奮 顯示的是目前最後一個 token 在第 1 層的實際數值
等待開始…

Step 5產生下一個字 Generation

最後一層的向量會跟字典裡每一個字比對，算出分數（logits）。除以溫度後做 softmax 變成機率， 只留下最高的 Top-K 個候選，再抽籤選出一個字。溫度越低越保守（幾乎都選第一名），越高越有創意也越容易亂講。

Step 6輸出並回到第一步 Output

選中的字被接回輸入的尾巴，然後整個流程再跑一次——這就是「自迴歸（autoregressive）」。 你看到 ChatGPT 一個字一個字吐出來，就是這個迴圈在轉。

那什麼時候停？模型自己決定。當它算出來機率最高的下一個字是句尾符號（這個模型是「。」）， 迴圈就結束——所以答案不會硬去塞滿你設定的長度上限。大模型用的是同一招，只是句尾符號換成字典裡一個專門的 <eos> token。把上面的「✂ 一句話講完就停」關掉，就能看到它硬撐下去會變成什麼樣子。

使用者手冊 — 「看得見的 LLM」動態演示頁

對象：要用這一頁講解／自學語言模型運作的人。 對應檔案：llm/index.html（單一檔案，約 280 KB，含這兩份手冊）。 模型規格：字典 755 字元、參數 134,976、2 layers × 4 heads、d=64、FFN 192、上下文 48 tokens。

1. 這一頁是什麼

一個單檔、零後端、離線可跑的網頁，用動畫一步一步演示語言模型從輸入到輸出的完整過程：

分詞 → 詞向量 → 注意力 → 前饋網路 → 取樣 → 輸出 → 回到分詞

畫面上的數字都是真的。 頁面內嵌一個從零訓練的 char-level GPT，權重直接寫在 HTML 裡，推論在你的瀏覽器即時進行。不是預錄動畫，也不呼叫任何 API — 拔掉網路線一樣跑。

它不是什麼： 不是聊天機器人。這個模型只有 13 萬參數、只讀過 437 句 III/V 磊晶與 SPC 的中文短句，它會做的事就是「把很像訓練語料的句子接下去」。問它今天天氣，它會用磊晶的語氣胡說八道 — 那正是要給人看的東西。

2. 怎麼打開

直接用瀏覽器開啟 index.html 就好，不需要架站、不需要安裝任何東西。

  • 雙擊檔案，或拖進瀏覽器視窗。
  • 放在網路磁碟、隨身碟、公司內網都可以；整份內容都在這一個檔案裡。
  • 需要支援 canvas 與 ES2017 的瀏覽器（Chrome / Edge / Firefox / Safari 近幾年的版本都可以）。
  • 手機可以看，版面會自己收窄（測試過 390px 寬）；但熱圖較小，投影講解建議用桌機。

若系統設定了「減少動態效果」（prefers-reduced-motion），CSS 轉場會被關掉，畫面改為直接跳到結果 — 內容一樣完整。

手冊就在頁面裡。 這兩份文件收在頁面最下面的「附錄：手冊」，離線也讀得到；標題底下有直達連結。所以把 index.html 一個檔案交給別人就夠了，不必再附說明。

4. 五分鐘上手

  1. 開啟頁面。首屏已經先靜態畫好一組預覽（用「MOCVD 的成長溫度」跑的），可以先讓聽眾看一眼六個步驟長什麼樣。
  2. 按 ▶ 開始演示（或按空白鍵）。
  3. 畫面會自動捲到 Step 1，然後一路往下走到 Step 6，再回到 Step 1 產生下一個字。
  4. 想停下來講解就按 ⏸ 暫停（空白鍵）；要重來按 ⏹ 停止（Esc）。
  5. 講完一輪後，把溫度拉高到 1.8 再跑一次，讓聽眾看同一個提示怎麼變得語無倫次 — 這是最有效的對照。

6. 六個步驟各在演示什麼

Step 1 — 分詞 Tokenization

輸入被切成一個個 token，查表換成 id。chip 會逐一飛入。

該看的： MOCVD 被切成 5 個 token，而中文一個字只佔 1 個。英文和數字天生就比中文吃 token。

讀數列出最後 12 個 id 與字典大小。

Step 2 — 詞向量 Embedding

三張熱圖：詞向量 ＋ 位置向量 ＝ 輸入向量。橘色是正、藍色是負、暗灰是 0（發散色標，圖例在右下）。

該看的： 同一個字在不同位置，第三張圖的顏色不一樣 — 位置資訊是加進去的，不是天生就有。

讀數列出最後一個字向量的前 6 維實際數值，以及詞向量表的參數量（755×64 = 48,320）。

熱圖最多顯示 14 個 token；序列更長時只畫最後 14 個。
Step 3 — 注意力 Attention

T×T 的熱圖逐列畫出，右側長條列出相同數值。上方有 2 層 × 4 頭 = 8 個按鈕可以切換。

該看的：

  • 右上角是空白的 — 那是未來的字，被因果遮罩擋住了，模型不能偷看後文。
  • 切不同的頭，亮的位置不一樣 — 每個頭在看不同的關係。
  • 讀數會直接告訴你「這個字把百分之幾的注意力放在哪個字上」。

切換頭的按鈕在暫停或停止之後仍然有效，會用最後一次的計算結果重畫 — 適合停下來逐頭講解。

Step 4 — 前饋網路 FFN

64 維 → 192 維 GELU → 壓回 64 維，連線與激活長條分段動畫。

該看的： 讀數會報「有幾個神經元幾乎沒被點亮」— GELU 把它們關掉了。以及這一層的參數量（2×64×192 = 24,576），佔整個模型一大半。

這一格畫的是最後一層（第 2 層）最後一個 token 的實際數值。
Step 5 — 產生 Generation

Top-K 機率長條 ＋ 轉盤抽籤 ＋ 亂數指針。

該看的：

  • 長條是套用溫度之後、只留 Top-K 的機率。
  • 轉盤每一段的寬度就是該字的機率；指針落在哪一段就選哪個字。
  • 讀數同時給出「最高分的是誰」與「實際抽到誰」— 兩者不一定一樣，這就是為什麼同一句話每次跑結果會不同。
  • 最後那個 熵（bits） 是這一步的不確定性，對整個字典算的：

- < 0.15 幾乎沒有懸念 - < 1 有點猶豫 - < 2.5 相當不確定 - 更高 = 完全不知道要接什麼

把溫度拉高再看同一格，熵會明顯變大 — 這是溫度在做什麼最直觀的證據。

Step 6 — 輸出 Output

新的字接回輸入，箭頭閃一下，回到 Step 1。這就是自迴歸生成：P(下一個字 | 前面所有字)。

讀數會告訴你這一輪是講完了才停，還是跑到上限被截斷。

7. 什麼時候停：模型自己決定

這一頁的「產生長度上限」是上限，不是目標值。訓練語料裡每一句都以「。」結尾、再用換行分隔，所以這兩個字元就是這個模型學到的「講完了」。產生迴圈看到它們就收工。

上限設 120 字，六個範例實際跑出來：

提示實際長度產出
MOCVD 的成長20 字MOCVD 的成長溫度通常在 600 到 750 度之間。
Cpk 大於16 字Cpk 大於 1.33 代表製程的能力足夠。
PL 的波長14 字PL 的波長是磊晶最重要的管制項目之一。
連續七點14 字連續七點持續上升或是下降代表有趨勢。
量子井的9 字量子井的厚度只有幾個奈米。
今天天氣12 字今天天氣很冷，記得多穿一件衣服。

講解時值得帶到的一點： 大模型也是同一招，只是句尾符號換成字典裡一個專門的 <eos> token — 訓練時擺在每個樣本結尾，模型學會「該收尾了就吐它」。ChatGPT 回答完會停下來，不是因為有人數了字數，是模型自己判斷講完了。

把 ✂ 一句話講完就停 關掉，就能看到它硬撐下去會變成什麼樣子：通常是接著開始講下一句，因為訓練資料本來就是一句接一句。這個對照很直觀。

9. 這個模型的邊界（講解時值得先講清楚）

  • 只會這個領域。 語料是 437 句、45,780 字的 III/V 磊晶 ＋ SPC ＋ 良率可靠度 ＋ 金融財經中文短句。領域外的輸入它會硬接。
  • 會記錯數字。 例如偶爾吐出 Cpk 大於 1.63，而正確數字在那一格有 97.5% 的機率 — 是 0.2% 的候選贏了抽籤。這正是「幻覺」的縮影：不是不知道，是抽樣抽到了冷門。
  • 有些歧義訓練不掉。 例如「複利是利息」下一格，， 58.8% 對上 再 31.0%（正解是「再」）。char-level ＋ 48 tokens 的前綴訊息量壓不過「利息 → ，」這個先驗，多訓練也不會改善。
  • 規模差距。 這個模型 13 萬參數；真正的 LLM 是十億到兆級。演示的是機制，不是能力。

2. 模型規格

從 weights.json 的 cfg 讀出：

欄位值意義
V755字典大小（字元數）
C64向量維度
L2層數
H4每層的注意力頭數
F192FFN 隱藏層維度
B48上下文長度（tokens）

HD = C / H = 16（每個頭的維度）。

參數量公式：

V·C  +  B·C  +  L·(4C² + 2C·F + 9C + F)  +  2C

代入：48,320 + 3,072 + 2×41,728 + 128 = 134,976。

各項對應：詞向量表 V·C、位置向量表 B·C、每層的 QKV＋輸出投影 4C²、FFN 兩個矩陣 2C·F、兩組 LayerNorm 的 γ/β 與三組 bias 9C + F、最後的 LayerNorm 2C。

注意 H 不在公式裡 — 改頭數不會改變參數量，只是把同樣的 C 維切成不同份數。這一點在頁面上有八個切換按鈕（L × H），講解時值得指出來。

輸出頭是 weight-tied 的：logits 直接用 wte 算，沒有獨立的輸出矩陣。

3. 權重檔格式

weights.json 結構：

{
  "cfg":   { "V":755, "C":64, "L":2, "H":4, "F":192, "B":48 },
  "vocab": ["\n", " ", "!", …],          // 長度 V，index 即 token id
  "tensors": {
    "wte":  { "s": 0.0123, "d": "<base64>" },   // s = scale，d = int8 資料
    "wpe":  { … },
    "layers.0.ln1g": { … }, "layers.0.ln1b": { … },
    "layers.0.wqkv": { … }, "layers.0.bqkv": { … },
    "layers.0.wo":   { … }, "layers.0.bo":   { … },
    "layers.0.ln2g": { … }, "layers.0.ln2b": { … },
    "layers.0.w1":   { … }, "layers.0.b1":   { … },
    "layers.0.w2":   { … }, "layers.0.b2":   { … },
    "layers.1.…":    { … },
    "lnfg": { … }, "lnfb": { … }
  }
}

共 28 個張量（2 + 12×2 + 2）。

量化：int8 對稱量化。 每個張量存一個 scale s 與一串 int8。反量化就是 value = int8 × s：

function deq(t) {
  const bin = atob(t.d), n = bin.length, out = new Float32Array(n);
  for (let i = 0; i < n; i++) {
    let b = bin.charCodeAt(i);
    if (b > 127) b -= 256;        // base64 解出來是 0..255，要還原成有號
    out[i] = b * t.s;
  }
  return out;
}

因為一個參數剛好一個位元組，參數量就等於所有 base64 解碼後的總長度 — 頁面上的「參數量」規格就是這樣算出來的，不是寫死的數字：

const N_PARAMS = Object.keys(RAW.tensors)
  .reduce((a, k) => a + atob(RAW.tensors[k].d).length, 0);

4. 推論實作

forward(tokens) 是純 JS 的前向傳播，與 train.js 的實作等價，差別只在它把所有中間值留在 cache 裡供繪圖使用。

架構是 pre-LN Transformer decoder：

emb = wte[token] + wpe[position]
for each layer:
    ln1  = LayerNorm(x)
    qkv  = ln1 @ Wqkv + bqkv                       # 一次算出 Q/K/V
    for each head:
        scores = (Q·K) / √HD,  只算 s ≤ t          # 因果遮罩：直接不算未來
        att    = softmax(scores)                   # 減去最大值再取 exp
        out    = Σ att·V
    res1 = x + (attout @ Wo) + bo                  # 殘差
    ln2  = LayerNorm(res1)
    fc   = ln2 @ W1 + b1
    act  = GELU(fc)
    res2 = res1 + (act @ W2) + b2                  # 殘差
    x    = res2
lnf    = LayerNorm(x)
logits = lnf[最後一個 token] · wteᵀ                # weight-tied

實作細節：

  • LayerNorm 用 eps = 1e-5，逐 token 算均值與變異數。
  • GELU 用 tanh 近似：0.5x(1 + tanh(√(2/π)(x + 0.044715x³)))。
  • 因果遮罩不是乘 0，而是內層迴圈只跑到 s <= t — 未來的位置根本沒被計算，所以熱圖右上角是真的空白。
  • softmax 先減最大值再取 exp，避免溢位。
  • logits 只算最後一個 token（生成只需要這一格），這是主要的省時處。
  • matmul 是樸素三層迴圈，但跳過 a === 0 的項。序列最長 48、C=64，這個規模不需要分塊或 SIMD。

cache 保留的東西（繪圖層直接讀）：

欄位內容
tokv / posv / embStep 2 的三張熱圖
blocks[l].scores / .attStep 3 的注意力（softmax 前 / 後）
blocks[l].ln2 / .fc / .act / .foStep 4 的 FFN 輸入、線性輸出、激活、輸出
logitsStep 5 的候選分數

Step 4 固定畫最後一層（L = CFG.L - 1）最後一個 token。

5. 取樣

function softmaxTopK(logits, temperature, K) {
  const idx = [...].sort((a, b) => logits[b] - logits[a]);   // 對全字典排序
  const keep = idx.slice(0, K);
  // 只對留下的 K 個做 softmax(logit / temperature)
}

兩點值得知道：

  1. Top-K 是對原始 logits 選的，不是對溫度縮放後選的 — 正溫度不改變排序，所以兩者等價，但實作上先選再縮放比較省。
  2. 回傳的機率是「在 K 個候選之內」的機率，加總為 1。所以 Top-K 從 8 改成 3，同一個字的百分比會變大 — 那是重新歸一化，不是模型變有把握了。

熵另外算，而且是對整個字典算的（不是只算 Top-K），單位 bits：

H = -Σ p·log₂(p)     // p = softmax(logits / temperature) over all V

這是頁面上唯一能反映「模型對整體有多猶豫」的數字；只看 Top-K 的長條會嚴重低估不確定性。

停止條件
const STOP_CHARS = new Set(['。', '\n']);

語料是 437 句、每句以「。」結尾、用 \n 串起來（corpus.js 的 buildCorpus()），所以這兩個字元就是這個模型學到的句尾。產生迴圈在 tokens.push(next) 之後檢查，命中就 break：

if (stopAtEos && STOP_CHARS.has(VOCAB[next])) { hitEos = true; break; }

因此 len 滑桿是上限而不是目標值。實測六個範例的產出落在 9–20 字，上限設 120 也一樣。

為什麼不需要另外加一個 <eos> token： 大模型會在字典裡放一個專門的結束符號，訓練時擺在每個樣本結尾。這裡「。」本來就在字典裡、而且在語料裡永遠出現在句子結尾，這個位置的統計已經足夠 — 加一個新符號只是多一個 embedding 要學。若日後語料改成句尾不一定是「。」（例如加入問句、條列），就得回頭改 STOP_CHARS，或真的加一個結束符號並重訓。

stopAtEos 由 #stopEosBtn 切換，關掉之後會一路跑到上限 — 保留這個開關是為了能演示「不停下來會變成什麼樣」。

抽樣是累積機率法：r = Math.random()，沿著 probs 累加，第一個超過 r 的就是選中的字。轉盤上指針的位置直接就是 r，所以畫面顯示的是真的抽籤過程，不是事後補畫。

6. 動畫執行器

三個機制撐起整個播放控制：

取消用 runId。 全域一個遞增的 runId，每次 start() / stop() 都 runId++。所有 await wait(...) 每一幀檢查 runId 有沒有變，變了就 throw CANCEL，整個 async 呼叫鏈自然拆掉。start() 的 catch 吞掉 CANCEL、其他錯誤照拋。

async function wait(ms) {
  const my = runId;
  let remain = ms, last = performance.now();
  while (remain > 0) {
    await raf();
    if (runId !== my) throw CANCEL;
    const now = performance.now(), dt = Math.min(80, now - last); last = now;
    if (!paused) remain -= dt * speed;      // 暫停 = 不扣時間
  }
}

暫停靠不扣時間，不是 clearTimeout — 所以暫停期間畫面完全凍住，繼續之後接得回去。dt 上限 80ms 是為了分頁切回來時不要一次跳完。

速度是乘在時間上的。 滑桿 5–40 → speed = 0.5 – 4.0，remain -= dt * speed。

詳細模式是一個係數。 runOnce(tokens, nPrompt, isFirst) 開頭算出 d：

const d = isFirst || detail ? 1 : 0.34;

之後所有 await wait(x * d)。第一個字永遠完整演示；關掉 detail 之後其餘的字約三倍速帶過。逐格揭露的動畫（Step 1 的 chip、Step 2 的逐行、Step 3 的逐列）則是用 isFirst 完全跳過。

7. 繪圖層

全部是 canvas 2D，沒有任何繪圖函式庫。

色標分兩種，依用途分工：

用途色標函式
有正負的向量（Step 2、Step 4 的輸入輸出）發散：藍 ← 暗灰 → 橘diverging(v, max)

縮放： 所有 canvas 都是 max-width:100%；resize 事件只重畫 Step 4（其他幾張在下一輪 runOnce 會自然重畫）。

8. UI 狀態

沒有框架，就是幾個模組層級變數：

let runId = 0, paused = false, speed = 1, detail = true, autoscroll = true, stopAtEos = true;
let running = false;
  • setStage(n) 切換六個 <section> 的 on / visited class 與步驟列的 active / done，並在 autoscroll 開啟時捲到該區塊（偏移 76px 讓開置頂步驟列）。
  • syncCtrl() 把主要按鈕的狀態同步到步驟列的迷你按鈕。
  • syncLenHint() 在產生長度、提示、或 stopAtEos / detail 改變時重算提示文字：stopAtEos 開著就說明這是上限、超過 CFG.B 就警告視窗會滑動、detail && n > 40 就警告會跑很久。
  • 鍵盤：Space = 開始／暫停、Escape = 停止；e.target.tagName === 'INPUT' 時直接 return（否則輸入框打不了空白）。

所有維度文案都從 cfg 填入，不是寫死的：規格列（specs）、.dimC / .dimF 這些 span、頁尾的參數量與語料字數。換一個不同規模的模型重新 build，頁面不會說錯自己的規格。

首屏會先靜態畫一次預覽（用 MOCVD 的成長溫度），Step 5 的預覽也讀控制列上的溫度滑桿 — 改預設溫度不會讓首屏跟實際演示對不起來。

9. 建置

cd llm/tools
node build.js ../index.html

build.js 做的事：

  1. 讀 weights.json 與 page.template.html，用 corpus.js 算語料字數，用 md.js 把兩份手冊轉成 HTML。
  2. 先檢查要內嵌的東西裡沒有 </script>（權重與手冊都檢查；有的話會提早關掉 <script> 標籤，整頁壞掉）。
  3. 先在模板上確認每個佔位符剛好出現一次，然後才置換（用函式形式的 replace，避免 $& 之類的替換樣式被誤解讀）。
  4. 寫檔，印出大小。
第 3 步刻意是「置換前數一次」而不是「置換後檢查殘留」。技術手冊本文就在講 __WEIGHTS__ 這些佔位符，那些字串會合法地出現在產出裡 — 用殘留檢查會誤判成置換失敗。這個坑是真的踩過才改的。
md.js：極小的 Markdown 轉換器

只支援 docs/*.md 實際用到的語法：標題、段落、清單、引用、水平線、表格（含 ---: 靠右）、程式碼區塊與行內程式碼、粗體、連結。刻意不做巢狀清單與圖片。

三個實作上的重點：

  • 行內程式碼先抽走再做其他規則，否則 `<eos>`、`</script>` 這種內容會被當成 HTML。佔位符用 \u0000 包住 — 一開始用「空白＋數字＋空白」，結果把正文裡的數字吃掉了。
  • 連結重寫：手冊互相引用（user-manual.md ↔ technical-manual.md）在頁內變成 #doc-user / #doc-tech 錨點；指向 repo 檔案的（../README.md）降成純文字，因為單檔網頁連不到。對照表在 build.js 的 LINKS。
  • assertNoMarkdown() 在轉完之後掃一遍產出，還看得到 **、| 開頭的行、# 標題、[](…) 就丟錯。加了沒支援的語法會讓 build 失敗，而不是默默出一頁壞掉的手冊。

表格一律包一層 .mdTableWrap（overflow-x:auto），否則手冊裡的寬表格在手機寬度會撐爆版面。

改完模板一定要重跑這個指令，否則 index.html 還是舊的。驗證有沒有生效最快的方法：看規格列的數字，或用瀏覽器搜尋你剛加的文案。

11. 效能與限制

  • 推論成本：每個字一次 forward。T ≤ 48、C = 64、L = 2，在一般筆電上單次 forward 遠低於一幀的時間；畫面速度完全由動畫節奏決定，不是被計算拖慢的。
  • 檔案大小 約 280 KB：權重 JSON 約 182 KB、兩份手冊約 24 KB、其餘是模板本身。int8 量化把浮點權重壓成四分之一；再往下壓（int4）會開始看得出生成品質變差。
  • 記憶體：forward 每次都配新的 Float32Array，沒有做緩衝池。以這個規模沒有必要，但如果把 B 或 C 放大一個數量級就得處理。
  • 沒有 KV cache：每產生一個字都重算整個序列。對演示反而是對的 — 要能畫出完整的注意力矩陣。真正的推論引擎不會這樣做。
  • 量化誤差：頁面顯示的數值是反量化之後的，與訓練時的浮點值有微小差異。不影響演示，但別拿頁面上的數字去驗證訓練程式。

12. 改完之後該驗什麼

Playwright 實跑過的項目，改動之後值得重跑一遍：

  • 桌機與 390px 手機寬度都沒有 console error、沒有水平溢出。
  • 產生流程能完整跑完；暫停真的凍住輸出；停止之後按鈕狀態正確復原。
  • 注意力頭切換會同步重畫（包含停止之後）。
  • 字典外的輸入會出現警告；全部都在字典外會拒絕開始。
  • 空白與換行字元在 Step 1 的 chip 與 Step 6 的輸出框裡都渲染正確。
  • 四個滑桿的上下限與提示條件（上限說明、超過上下文、詳細模式 > 40 字）。
  • 提早停止：開著 stopAtEos 時產出停在句尾符號且短於上限；關掉時剛好跑滿上限、句號不會中止。
  • 內嵌手冊：node md.js --test 全過；頁面上兩份手冊預設收起、標題連結與手冊內互相引用都會展開對應區塊、用 #doc-tech 開頁也會展開；展開後在 390px 仍無水平溢出（寬表格由 .mdTableWrap 自己捲）。
  • 實跑 60 字，確認滑動視窗之下續寫仍然完整。
